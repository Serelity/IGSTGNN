# P1报告—容量—传播通路诊断

2026-10-10。当前研究问题仍是“事故报告如何经由容量变化和传播改善IGSTGNN预测”。共同前9轮的最佳验证MAE中，P0相对N0改善约3.25%，P1相对P0改善约0.14%；这只是单种子、早期开发集信号，尚不能判定报告无价值或形成确认性结论。P1第10轮及L1后续轮次尚未完整回传。本步不续训，不以不同训练预算排名淘汰实验组。

入口：`experiments/chronological/probe_incident_capacity_reports.py`。仅增加诊断程序、测试和文档；17个冻结训练源文件及训练协议保持原字节。N1同样通过容量系数接收报告，与P1的主要区别是传播算子，不能称为直接特征拼接参照。

## 推理干预

只读取P1当前实际保存的`best_model.pt`，从检查点及训练历史核实最佳轮次，不假定一定是epoch9。单独审查P1，其他组未完成第10轮不阻止本步。支持summary落后于last checkpoint的情况，但两者必须保持严格历史前缀关系，最佳权重、预测和指标须与检查点历史一致；中断造成的半套最佳产物会被拒绝，不猜测或修复原文件。

先用原训练验证批量完整复现保存的ON预测及指标，通过后才允许任何OFF推理。之后默认沿用原验证批量和相同分组运行ON→OFF→ON，完整运行每组48条，工程检查每组2条，最后不足一组的样本保持原分组。每组保存实际ON/OFF预测；ON仍须与已核对的完整ON预测一致，末次ON须逐张量精确恢复全部预测及分支中间状态。

OFF只令新增报告容量系数回到该检查点的历史容量系数。原IGSTGNN的ICSF/TIID事故输入、历史观测、图、权重、初始状态和边界需求都保留。程序检查初始状态、历史编码、历史容量系数和边界需求逐位一致；无报告关联边的容量系数及容量逐位一致。其他边的通量、节点状态以及候选结构外的最终主干预测可能经传播或主干混合而改变，不能要求它们全部为零。

不构造优化器、不调用训练更新、不访问test，不改原检查点、summary、最佳预测或根identity。原六组已有训练产物在前后进行SHA256核对；检测到续跑锁时拒绝启动，运行中源产物发生变化也不能标记完成。该检查不是与任意外部训练器的事务锁，应在训练进程已经停止时运行。

允许记录与来源不同的推理设备/软件环境，不修改来源身份，不要求用户更换V100型号。来源身份、来源checkpoint的运行段、实际推理环境分别保留；源代码、数据、协议和初始化指纹仍严格校验。预测复现阈值预设为原流量单位`atol=1e-4, rtol=1e-6`，主MAE绝对差不超过`1e-4`，不得根据结果自动放宽。跨设备不能保证逐位复现，若未通过，程序记录失败并阻止OFF，不能把复现漂移解释成报告作用。

## 产物与解释

每次运行创建独立`report_capacity_probe_时间_随机码`目录。

| 文件 | 内容 |
|---|---|
| `invocation.json` | 来源身份、运行环境、输入目录、批量、阈值、脚本哈希及原产物哈希 |
| `checkpoint_audit.json` | P1轮次、历史、最佳权重/预测/指标与硬件运行段审查 |
| `replay.json` | 完整ON复现误差，通过后才写出 |
| `paired_predictions.npz` | 同批量ON/OFF预测、target、valid、样本/站点轴、报告支持掩码、截止点权重 |
| `pathway_curves.npz` | 系数、容量、交换通量、状态和融合增量的ON/OFF均值、带符号差及绝对差均值 |
| `samples.csv` | 每条样本的报告匹配数量、支持范围、报告年龄和配对误差 |
| `report.json` | 完成报告、覆盖率、分层/分预测步长误差、传播诊断与状态保持结果 |
| `failure.json` | 发生错误时的原因和原产物保持检查；不构成完成结果 |
| `paired_on_replay_failure.json` | 配对ON复现失败时的原/诊断批量、验证行、超限位置数、最大偏差和最严重位置的允许误差 |

主评价继续采用原指标：每个预测步长先在有效样本×站点上汇总MAE，再对12个步长平均。始终使用相同target和valid。`off_minus_on_mae > 0`表示在该检查点及这些观测上开启报告更好，负值表示关闭更好；原预测窗口为截止点后的`[5,10]`至`[60,65]`分钟，不错标为`[0,5]`至`[55,60]`。

分组包括全496站、共同/新增/候选外结构、道路、报告边端点、潜在传播区域、报告匹配/不匹配的样本及记录报告年龄段。分组由输入和结构确定，不按误差挑区域；空区域或某预测步长没有有效观测返回`null`，不填零。

潜在传播区域定义为报告关联内部边端点所在的弱连通分量，去掉直接关联端点；它包含可能的上游接收约束作用，外部端点-1不会把不同道路分量连起来。这只是宽泛结构包络，没有传播时长/速度认证，更不是实际事故影响真值。没有直接报告关联也不等于没有事故影响。

报告年龄使用截止点前60分钟集合中最年轻的匹配报告记录年龄，年龄分组为`[0,5)`、`[5,15)`和`[15,60]`分钟，不能称为事故发生初期/恢复期。记录时间和首报位置可见性仍是原数据的离线假设；不新增持续时间、处置、封道或严重程度标签。

同时提供每条样本`1/同一t0样本数`的截止点加权敏感性结果，原指标不被替换。不同截止点仍可能有重叠，程序不把这些样本当独立试验，不提供伪精确的显著性结论。

路径诊断分四环节：报告匹配覆盖；容量系数/曲线；共享通量及潜在状态；最终预测。容量、通量和状态是模型内部潜变量，不能解释成已校准的车辆单位。曲线按原样本等权汇总，潜在通道取平均，四个容量系数分别保留；同时保留绝对差均值，避免正负抵消。另给直接报告边的容量/通量变化统计和容量、发送、接收限制率及明确分母。`1e-7`只是描述数值变化的阈值，不是显著性检验。路径曲线中的`off_minus_on`表示相应潜变量的OFF−ON，不应与MAE差混用解释。

同检查点开关回答“训练好的模型如何依赖报告”，不能替代独立训练的P0/N0消融，也不能证明现实因果。后续按断点只修改一个环节，再在相同预算下比较N0/N1/P0/P1。局部有收益而全局变化小时，应先核对覆盖和指标稀释；容量改变但通量不变时，应先检查约束是否生效，而不是立即加更复杂模块。

数据、传感器及报告元数据沿用既有默认路径；网络包默认为原运行目录下的`network_pack`。路径不同可显式传`--data-dir`、`--sensors`、`--network-dir`、`--report-bundle`，指纹必须与原运行一致。完整ON复现和后续诊断默认均采用原验证批量48，工程检查均为2。仍可显式指定`--probe-batch-size`，但改变分组也会改变报告填充及数值运算形状，可能使严格复现失败；自定义批量不自动放行或放宽阈值。每次输出目录唯一，失败后重新运行会建立新目录并保留旧失败证据。

结束时终端打印轮次、关键区域的ON/OFF MAE、逐预测步长差、容量/通量/状态变化、覆盖率和报告路径，回传这段输出即可开展第一轮分析。本地首4条真实验证样本仅用于程序验收；服务器完整917条的科学分析结果尚待运行。

## 开发验收

12项新增诊断测试与83项原有容量训练、输入、传播、融合、续跑和硬件迁移回归共95项通过，无跳过。新增测试覆盖独立移除报告的等价性、原事故输入保持、无报告样本精确回退、推理/梯度边界、ON复现失败阻止OFF、末次恢复失败阻止产物完成、流式曲线独立核算、指标符号/汇总/空区域、截止点权重及Windows/Linux产物路径键。

初版真实数据验收使用本地原M4.2工程运行的P1 epoch1最佳检查点和首4条验证样本，保留全部496站。原验证批量2复现保存预测的最大差为0；当时默认诊断批量8实际处理4条时，ON相对原批量最大差为`9.1553e-5`原流量单位，主MAE差为`1.6984e-7`，均在预设阈值内。该检查未覆盖服务器完整917条中的批量变化风险。配对误差保存的是实际同批量ON/OFF，避免把批量数值差当作报告贡献。32个原训练产物哈希保持一致，模型状态及末次ON恢复检查通过。

该工程样本中，报告调制改变了容量系数和容量，但交换通量、状态和最终预测没有改变，直接报告边的容量限制率为0。这说明程序能辨别通路在哪一环没有响应；不能据此推断服务器epoch9模型或完整验证集。验收详情见[机器记录](incident_capacity_report_probe_m44_20261010.json)，真实SXM2→PCIE跨GPU复现与服务器完整验证仍未在本地代做。
