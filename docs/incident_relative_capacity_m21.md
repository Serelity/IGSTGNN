# M2.1：共享相对容量状态工程原型

2026-10-09。先冻结以下接口和假设，再实施代码及检查。**M2.1工程原型已完成：14项测试、CPU全候选X检查、GPU完整Bash流程均通过。** 本任务交付容量状态模块与同输入普通状态参照；IGSTGNN融合、空间传播、新Y和正式训练属于后续任务。

## 状态、输入和观测的分工

| 对象 | 定义与单位 | 本阶段边界 |
|---|---|---|
| 历史X | `[B,12,N,3]`，源流量/占有率/速度，附布尔掩码 | 仅截止时刻之前的历史；不增加事故类型、事后持续时间等字段 |
| 参考尺度 | 每站每通道、候选训练X唯一时间上的p95，源单位 | 冻结读取M1.0c结果；只是数值尺度，不是容量 |
| 历史状态z | 共享GRU编码`asinh(X/reference)`及掩码 | 无量纲隐状态，不声称密度或队列；无逐站可学习参数 |
| 报告条件 | `report_location_v1`的关联分数、源PM侧别、报告年龄（分钟） | 关联不是影响真值；PM侧别不冒称上下游；不回填报告到历史GRU |
| 容量保留比例r | 相对未受该新增报告条件影响的基准，范围`[0.05,1]` | 无量纲假设，不输出车辆/小时容量；关闭新增条件时严格为1 |
| 外部供需算子 | `f=min(d,c0*r,s)`，四项共用一个明确的流量尺度 | 本阶段只用人工给定的合成供需，检查限制行为；不从真实历史直接构造d、s、c0 |

输入里没有学习图、长度或匝道流量。此模块逐站共享执行，支持任意N；全496站都保留。没有某站完整历史时输出中性状态并明确标记，不能将其算作真实机制覆盖。部分缺失用零占位并传掩码，不当成真实零观测。

## 冻结的小规模参数化

`z=SharedGRU(history, mask)`；共享两层头读取`z`、报告关联分数、PM侧别以及`log1p(age/60)`，每站只输出两个标量`u0,u1`。没有事件专属需求、基准容量、密度或自由源汇头。

容量模式：`a=clamp(0.10+0.20*u0,0,0.95)`，`tau=5+175*sigmoid(u1)`分钟，`r(t)=1-support*a*exp(-t/tau)`。**a定义为截止时刻的扰动，不是事故发生时的扰动**；报告年龄只作可用条件，不把报告时刻等同事故起始。t是调用者显式传入的非负、严格递增的截止时刻后分钟数；工程检查取0,5,…,60，不冒称已对齐原预测目标区间。

单调恢复是本阶段的受限参照假设，不是数据事实；M2.2另行实现非强制单调低维轨迹。幅度可精确为0，clamp饱和区梯度为0，需后续记录饱和率。初始幅度约0.1仅为工程初始化，未校准；本模块未接入主干，所以不声称当前模块本身零初始化不改变预测。未来融合层需单独零初始化验收。

普通状态模式复用完全相同的输入、GRU、两层头、两个输出参数及参数量：`state(t)=1+support*(u0+u1*tanh(t/60))`。不加容量上下界或供需解释，用来控制额外输入、参数与低维时间展开；当前尚不是普通空间传播对照。容量模式的`state`就是r，后续两臂使用同样融合接口。

`incident_enabled=False`或无报告关联时，新增状态严格为1；历史编码不变、前向不修改输入/权重，不涉及原IGSTGNN的ICSF/TIID。历史中可能已有事故影响，因此条件关闭不是“无事故世界”的因果反事实。

## 本阶段验收与后续任务

检查零扰动、低需求、高需求容量下降与恢复、下游受限、无报告支持、全部/部分历史缺失、节点置换、正单位重标度、批量一致性、梯度、参数更新及模型/优化器保存恢复。负供需、未来报告年龄、非法尺度、时间轴和掩码错位必须拒绝。普通参照必须使用共同初始化并披露实际参数量。

真实候选X只进行无梯度接口检查，按全事件/全站批量运行，不读取Y或拟合容量。真实数据上的随机初始化r不作事故机制结论。数值检查通过只表明这个受限模块可运行，不能认证容量可辨识性、物理连接、守恒或预测收益。

## 实际完成与复现

模型代码：`src/models/incident_relative_capacity.py`；X适配器：`src/utils/relative_capacity_inputs.py`；工程入口：`experiments/chronological/check_incident_relative_capacity.py`。两种模式在hidden=16时均为**1506个可学习参数**，共同初始化完全一致，没有站号嵌入或逐站可学习容量。14项测试包括CPU/GPU状态一致性、梯度数值检查及模型/Adam继续更新重放，全部通过，没有跳过GPU项。

受控合成场景将截止幅度设为0.5、恢复时间常数设为30分钟、基准容量设为1（同一人为流量尺度）：

| 截止后分钟 | 容量保留比例 | 低需求0.2时流量 | 高需求2时流量 | 下游供给0.1时流量 |
|---|---:|---:|---:|---:|
| 0 | 0.5000 | 0.2 | 0.5000 | 0.1 |
| 30 | 0.8161 | 0.2 | 0.8161 | 0.1 |
| 60 | 0.9323 | 0.2 | 0.9323 | 0.1 |

这检验的是实现是否遵守指定限制关系，不是从真实事故估计出的恢复曲线。两臂各在人工目标上更新2次后保存，再比较恢复后的第3次更新：8个参数张量均获得非零有限梯度并更新，重放输出和续训参数最大差均为0。合成checkpoint明确标记`synthetic_only`，不得作为正式训练结果。

真实数据使用另一套全新初始化，CPU按全部9943事件×496站检查容量/普通模式及条件开/关，耗时约76.5秒；14道路方向组均保留，496站曾有可用历史与报告支持。全部数值有限，容量范围、无支持处中性、关闭条件中性均通过，参数未改、无梯度、真实数据更新数0。当前输出时间是0—60分钟的13个状态采样点，不是原12步流量预测。未加载新Y、验证或测试。

真实完整检查输出：`experiments/chronological_runs/contra_capacity_m21_20261009_v1`。另在本机RTX4060 Laptop GPU、Python3.10.18、PyTorch2.3.1执行完整Bash测试与GPU合成检查，输出 `experiments/chronological_runs/contra_capacity_m21_20261009_183238_Wi43Rq`，退出码0；该GPU流程未重复真实X检查，也不是服务器V100验证。初次直接测试同样14项通过。汇总证据见[机器记录](incident_relative_capacity_m21_20261009.json)。

服务器激活原环境、在代码仓库运行以下命令即可做合成工程检查，不需要新候选包：

```bash
bash experiments/chronological/run_incident_relative_capacity.sh
```

默认CPU；若已在Slurm GPU allocation中，可前置`CAPACITY_DEVICE=cuda:0`。可用`CAPACITY_PYTHON`指定现有Python。若要同时核对全候选X，将本地已构建包的服务器路径作为唯一参数：

```bash
bash experiments/chronological/run_incident_relative_capacity.sh "$CANDIDATE_X_DIR"
```

脚本没有Git、网络、安装或提交调度作业；不自行寻找不同数据代替指定包。完整候选数组仍只留本地，推送代码不会把它自动同步到服务器。本轮本地已完成，无须为了进入后续开发再重复服务器检查。

## 思想来源与方法记录

供需/容量限制借鉴[Daganzo CTM前驱报告（封面1993年7月）§2、§3](https://escholarship.org/content/qt0b6612tk/qt0b6612tk.pdf)。该文采用积累及相邻界面递推；本模块只实现容量条件和一个限制算子的合成检查，不能称完整CTM。指数恢复沿用仓库H1受限参照；全网共享的相对状态接口与上述普通参照是本研究的待检验设计，不宣称文献已验证或具有新颖性。

延续`uncertainty-and-units`技能检查量纲与观测含义，未知误差不编造置信区间。工具方法来源：Kassis, T.; Agarwal, V.; He, Y.; Patel, D.; Brueckner, A. M. (2026), [Scientific Agent Skills](https://doi.org/10.48550/arXiv.2609.00065)，2026-10-09复核当前记录；不是交通模型有效性证据。
